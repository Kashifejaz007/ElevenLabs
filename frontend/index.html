Security Architecture

The trust boundary that matters most in this system.

CUSTOMER │ ▼ VOICE / TELEPHONY │ ▼ ELEVENLABS AGENT (conversation, language, intent — nothing security-critical) │ ▼ ELEVENLABS WORKFLOW │ ▼ SECURE WEBHOOK │ ▼ RESOLVEAI POLICY / GUARDRAIL ENGINE (this is the trust boundary) │ ▼ BANKING SANDBOX API (freeze, transaction state) │ ▼ AUDIT STORE
LLM DOES NOT CONTROL SECURITY DECISIONS.
BACKEND POLICY ENGINE IS AUTHORITATIVE.

The model can request. The backend decides. Verification is a server-side code comparison, never an agent-asserted boolean. Card freezes above a value threshold require human authorization — full customer confirmation is not enough on its own.

Why It's Designed This Way

Why no PIN?

A PIN is the one thing a real bank never asks for over an unsolicited call. Requesting one is itself a fraud pattern — so this agent never has a tool capable of collecting, checking, or storing one.

Why backend verification?

An LLM can be persuaded. A server-side string comparison against a code that never reaches the model cannot be talked out of its answer.

Why no approve/transfer tool?

The safest way to guarantee an action never happens is for the function that would perform it to not exist on the tool surface at all.

Why a human authorization gate?

Above a value threshold, even a fully confirmed customer call shouldn't authorize an action alone — that mirrors real four-eyes banking controls.

Why idempotent freezing?

A voice call can retry, glitch, or repeat itself. Freezing twice must never behave differently from freezing once.

Why audit everything?

Every security-relevant action — allowed or blocked — is logged, so any call can be reconstructed and reviewed after the fact.

Honesty note: this is a sandboxed proof of concept. Card, customer, and transaction data are entirely fictional. No real banking core system, card network, or financial transaction is connected. What's real: the guardrail logic, the state machine, the audit trail, and every backend call this page makes.
